# MiMA: notes for AI agents and new developers

MiMA (Model of an idealized Moist Atmosphere) is an intermediate-complexity GCM in Fortran 90:
the GFDL spectral dynamical core, RRTMG or gray radiation, Betts-Miller convection, a slab
ocean and land, and Held-Suarez forcing. It is built with CMake against the external NOAA-GFDL
FMS library (2026.01.01 or later; FMS 2026.02 is downloaded if none is found). Branch `v2` is
the v2.0 release candidate; `main` is v1.2.x. The user documentation is in `docs/` (MkDocs);
read `docs/GettingStarted.md` and `docs/DynamicalCore.md` before touching the core.

## Directory map
- `src/coupler/coupler_main.f90`: the main program (time loop, `RESTART/`)
- `src/atmos_coupled/atmos_model.f90`: the atmosphere driver called by the coupler
- `src/atmos_spectral/`: dynamical core: `atmosphere/` (driver and physics call sequence),
  `dynamics/` (time step, implicit, damping, pressures), `diagnostics/`, `init/` (cold start,
  vertical coordinate, topography, initial noise), `transforms/` (spectral transforms, FFT, MPI
  decomposition)
- `src/atmos_param/`: physics (physics_driver, radiation/ with rrtm/ and gray, betts_miller,
  lscale_cond, moist_conv, moist_processes, cg_drag, mg_drag, damping_driver, held_suarez,
  local_heating, vert_diff, diffusivity, monin_obukhov, diag_integral)
- `src/atmos_param/radiation/rrtm/rrtmg_{lw,sw}/`: vendored AER RRTMG. Edit only with minimal,
  `!mima`-marked changes; never reformat.
- `src/surface/`: flux_exchange, ocean_model, land_model, surface_albedo, ocean_qflux, surface_flux
- `src/atmos_shared/`: interpolator (ozone, SST, Q-flux files), tracer driver, vertical advection
- `src/mima_shared/`: restart_file (restart layout), namelist_check (scan input.nml for removed keys)
- Every `src/**/CMakeLists.txt` lists its source files: add new files there.
- `cmake/MiMAFMS.cmake`: FMS find-or-fetch (version and SHA256 pin); `cmake/FindNetCDF.cmake`
- `input/`: the default RRTM test case and the template for a new run (`input.nml`, `diag_table`,
  `field_table`, `INPUT/` data). `examples/{gray,held_suarez}/`: other complete configurations.
- `tests/`: the committed CTest suite (see Testing). `tests/regression/` and `.v2-notes/` are
  local-only development leftovers listed in `.git/info/exclude`; never commit them.
- `docs/*.md`, `mkdocs.yml`: the documentation site. `docs/Parameters.md` and `docs/Diagnostics.md`
  are generated by `tools/mimadoc` between `<!-- mimadoc -->` markers (the prose outside the
  markers is hand-written). `tools/fortran_api.py` (MkDocs hook, FORD as parser, `ford.md`)
  generates the API reference pages from the doc comments.

## Build and run
    cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DINSTALL_EXEC=ON
    cmake --build build -j 8
    cmake --install build        # INSTALL_EXEC=ON: ready-to-run exec/ (mima, input files, INPUT/, RESTART/)
    cd exec && ulimit -s unlimited && mpirun -n 4 ./mima     # macOS: ulimit -s hard
- Release is the default build type. `-DMIMA_OPENMP=ON` threads MiMA's loops (default OFF);
  keep ranks x threads <= cores. `-DMIMA_RUN_CONFIG=examples/gray` installs another configuration.
- Installed FMS: `-DCMAKE_PREFIX_PATH=<prefix>`. Offline: `-DFETCHCONTENT_SOURCE_DIR_FMS=<FMS source>`.
- Compilers come from `FC`/`CC` at the first configure; delete `build/` after changing them.
- The number of ranks must divide the number of latitudes (64 at T42). A run directory needs an
  existing `RESTART/`. The shipped case is a 360-day year (about an hour on 4 cores); use
  `days = 0, hours = 10` in `&coupler_nml` to try things out.
- Do not run the model unless a result depends on it; verify most changes by building and
  re-reading the diff. Never put run output under the source tree; delete it when done.

## Testing
    cmake -S . -B build -DMIMA_TESTING=ON && cmake --build build -j 8
    ulimit -s hard; ctest --test-dir build --output-on-failure      # about 2 minutes
- `tests/README.md` explains the tests: smoke runs of the shipped configurations, restart =
  continuous, code defaults = `input/input.nml`, start-up guards, and `compare_<case>` against a
  reference build's digests (`-DMIMA_TEST_REFERENCE=<dir>`). The runner `tests/run_case.sh`
  enforces the rules: output only under the build tree or `$TMPDIR`, deleted on success; at most
  one run per user at a time; ranks never exceed the cores; a 300 MB cap per run.
- The bar for refactors and clean-ups is **bit-for-bit**: build a reference from the previous
  commit, digest it, and `compare_*` the working tree against it. Digests are machine- and
  compiler-specific, so they are never committed.
- Run at most one test suite at a time on a machine, and never from several agents at once.

## Fortran conventions
- Style: fprettify 0.3.7 with `.fprettify.rc` (2-space indent, lower-case keywords, `==`/`/=`,
  spaces around `+`, `-` and relational operators, none around `*` and `/`). If fprettify is not
  installed, format by hand to the same rules.
- Doc comments: `!>` before an item, `!!` after a declaration. They feed the API pages (FORD) and
  the namelist and diagnostic references (mimadoc). Every namelist variable needs a `!!` comment
  with its meaning, [units] and allowed values. See `docs/FortranAPI.md#writing-doc-comments`.
- Namelist defaults in the code must equal the values in `input/input.nml` (the test
  `defaults_rrtm` checks this).
- After touching a namelist or a `register_diag_field` call: `python3 tools/mimadoc generate`,
  then `python3 tools/mimadoc check`, and commit `docs/Parameters.md` and `docs/Diagnostics.md`.
- After changing a shipped `diag_table` or `input.nml`:
  `python3 tools/mimadoc validate <diag_table> --nml <input.nml>`.
- User-visible changes go in `docs/Versions.md` (v2.0 list) and `docs/Migration_v2.md`
  (with "Changes to the answers" for anything that changes results).
- Removed namelist keys are caught with `namelist_check_mod` so that an old `input.nml` stops
  with a message pointing to the migration guide.

## Changing answers
- Never fix a bug that changes the answers of a shipped configuration silently. Propose it to the
  owner first (what, why, which configurations, measured impact), and apply it only after approval.
- Each answer-changing fix gets its own commit so that it can be attributed and re-baselined.
  Bit-for-bit refactors and answer-changing fixes are never mixed in one commit. A fix that
  changes answers only for an option that no shipped configuration uses is acceptable, but the
  commit body must say so.
- Hoisting invariant work out of loops is fine only if every value is computed by the same
  expression in the same precision and order.

## Commits and git
- Subject: imperative, sentence case, no trailing period, usually under 80 characters, no prefix;
  cite bug IDs in parentheses, e.g. "Use the signed latitude in albedo_choice = 5 (BUG-95)".
- Body: wrapped prose explaining what changed and why, and whether it is bit-for-bit or how the
  answers change.
- Stage with explicit paths and commit with `git commit -- <paths>`; never `git add -A` or
  `git commit -a`. Several agents may share one working tree, and a plain `git commit` takes
  whatever another agent has staged.
- Commit only when asked; never push without the owner.

## Versions and release files
- The version is in `CMakeLists.txt` (`project(MiMA VERSION ...)`), `ford.md` (`version:`) and
  `CITATION.cff` (`version:`). In `CITATION.cff`, `cff-version` is the schema version (1.2.0):
  never bump it. Set `date-released` at the tag.
